## Context

A start page for self-hosted services is a solved problem in the sense that several projects do it, and an unsolved one in the sense that each asks for something the GitOps user does not want to give: a database, a build step, a published image, or a pod restart per config edit.

The constraint that shapes every decision below: the target user already runs Flux or Argo CD, and does not want another image to track. They want to point at a git ref, add a ConfigMap, and be done. That rules out a bundler, a transpiler, a server-side runtime, and anything that needs a registry.

## Goals / Non-Goals

**Goals:**

- Install is a remote kustomize base plus one ConfigMap. No image build, no registry, no chart required.
- A config edit is visible in the browser without a pod restart and without a page reload.
- Arbitrary nesting of groups, and named sets that open many targets at once.
- Correct and pleasant from a 320px phone to a wide desktop, in light and dark.
- Config authored in YAML (or JSON), validated with errors shown on the page, never a blank screen.
- Auditable: no CDN, no telemetry, no analytics, no outbound request the user did not configure.

**Non-Goals:**

- **No iframe embedding of apps.** Framing other apps in the portal requires `frame-ancestors` and `X-Frame-Options` changes on every embedded app, and interacts badly with any auth in front of them. That is a per-deployment security decision, not a default. Revisit as its own capability.
- **No service health/status indicators.** A browser cannot read the status of a cross-origin response without CORS headers on the target, and every workaround (opaque `no-cors` fetches, image probes) reports failure for working services and success for some broken ones. A status dot that lies is worse than no status dot. The projects that do this well do it from a server; we have no server by design.
- **No authentication.** The page is static and public to whoever can reach it. Put it behind ingress auth.
- No per-user state on a server. Collapse state and theme are per-browser.
- No bundler, no transpiler, no framework, no `node_modules` at runtime.

## Decisions

### Build-free, framework-free, ES modules

Plain HTML, CSS and ES modules served as-is. The point is that an operator can read and tweak the thing, and that the files can be mounted straight from a ConfigMap. A bundler would reintroduce the build artifact we are trying to delete.

*Alternatives:* Vite plus a published image (config changes still need no rebuild, but every code change needs a release and a registry, and users must trust our image); a framework from a CDN (adds a third-party origin, breaks airgapped clusters, and fights the CSP below).

### Shipping the app as a ConfigMap, generated by kustomize

`deploy/kustomize/base` uses `configMapGenerator` over the files in `src/`. A remote base works because kustomize fetches the whole repo, so Flux's kustomize-controller and Argo CD both render it with no extra tooling. The generated name carries a content hash, so upgrading the app rolls the pod, while the user's own config ConfigMap is separate and does not.

Budget: a ConfigMap must stay under 1MiB, and the app plus the vendored YAML parser must stay well under that. Treat 300KiB of `src/` as the ceiling, enforced in CI.

*Alternatives:* an initContainer that downloads a release tarball (needs egress, defeats airgap); an OCI artifact (needs a registry, and the tooling is Flux-specific); committing a generated `configmap-app.yaml` (a duplicate of `src/` that drifts the moment someone edits one and not the other).

### Stock upstream nginx, pinned, with our own cache headers

`nginxinc/nginx-unprivileged` at a pinned tag, running as uid 101, read-only root filesystem with `emptyDir` for `/tmp` and `/var/cache/nginx`, all capabilities dropped, `RuntimeDefault` seccomp, no privilege escalation.

Our own `default.conf` ships as a second ConfigMap, because cache headers are load-bearing: the config file must be served `no-cache` with an `ETag` so live reload can revalidate cheaply, while `/assets/*` can cache for a year since the generator hashes the ConfigMap name and the pod rolls on change.

A strict CSP is set in the same conf: `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' https: data:; frame-ancestors 'none'; base-uri 'none'`. The `img-src https:` is the one concession, because user-configured favicons come from the user's own hosts. **Consequence for implementation: no inline `<script>`, no inline `style=`, and no `onclick=` attributes anywhere.**

*Alternatives:* Caddy (equally good, less universally present in homelabs); `busybox httpd` (no ETag, no header control); embedding the files in an existing pod (couples the portal to an unrelated release).

### Config: YAML or JSON, parsed in the browser, with a vendored parser

The browser parses the config, so YAML needs a parser in the page. `js-yaml` is vendored as its unminified ESM build at a pinned version, with the upstream version and a SHA-256 recorded in `THIRD-PARTY.md`.

Vendored rather than fetched: a CDN adds a third-party origin, breaks airgapped clusters, and violates the CSP above. Unminified rather than minified: this is a public repo and a reviewer should be able to read what we ship.

JSON needs no parser (`JSON.parse` is tried first, YAML only on failure), so a JSON-only user pays only the download.

*Alternatives:* JSON only (hostile to author by hand inside a ConfigMap, and every comparable project uses YAML); a hand-rolled YAML subset parser (~150 lines, no dependency, but it will mis-parse something real, silently, and the user will be blamed).

### Config schema, version 1

```yaml
version: 1                   # required; refuse a version we do not know
title: Home                  # page title and header
subtitle: ""                 # optional
theme: auto                  # auto | light | dark   (the user can override in the UI)
layout:
  density: comfortable       # comfortable | compact
  minCardWidth: 14rem
reload:
  interval: 30               # seconds; 0 disables live reload
groups:
  - id: media                # optional, derived from name when absent
    name: Media
    icon: "🎬"               # emoji/text, a URL, or "auto" for the origin favicon
    collapsed: false         # initial state; the browser remembers per id after that
    items:
      - id: library
        name: Library
        url: https://library.example.com
        description: Films and shows
        icon: auto
        tags: [streaming]
        target: _blank       # _blank | _self
    groups: []               # recursive, same shape
sets:
  - id: morning
    name: Morning check
    icon: "☀"
    targets: [library, dashboards, "https://status.example.com"]
```

`id` is the stable handle: sets reference items by `id`, and the browser remembers collapse state by group `id`. When omitted it is derived by slugifying the name within its parent path, so a rename moves the remembered state, which is the lesser evil versus demanding ids from everyone. Duplicate ids are a validation error rather than a last-one-wins surprise.

`targets` entries are item ids, group ids (meaning every item beneath, depth-first), or bare URLs.

### Live reload by ETag polling

`reload.js` polls the config URL on an interval (default 30s) with `If-None-Match`. A `304` costs almost nothing. On a `200` the body is hashed and compared before anything re-renders, so a new `ETag` on unchanged content is not treated as a change. Polling pauses while `document.hidden` and fires once immediately on becoming visible again. A manual reload control is always present.

30s is the right order of magnitude because kubelet itself takes up to about a minute to project a changed ConfigMap into the volume, so a tighter poll only burns requests.

Re-render preserves what the user is doing: scroll position, collapse state, the search query and focus. If a config change feels like a page reload, the feature is worse than restarting the pod.

**Two constraints this cannot work around:** a ConfigMap mounted with `subPath` is never updated by kubelet, and an `immutable: true` ConfigMap cannot change at all. Both are documented prominently, because both produce "live reload is broken" reports that are not bugs. The manifests we ship never use `subPath`.

*Alternatives:* WebSocket or SSE (needs a backend); a config hash in the pod template, or reloader-style annotations (both restart the pod, which is the thing being avoided).

### Open-all, and admitting that browsers fight it

`openSet` calls `window.open` synchronously inside the click handler, which is the only way the user gesture carries to every call. Browsers still cap this: `window.open` returns `null` when blocked, so the function returns `{opened, blocked}` and the UI lists the blocked targets as plain links the user can middle-click, with the reason stated. Sets above ten targets get a confirm step, since a mis-click otherwise opens a tab storm.

Pretending this always works, and silently dropping tabs, is the failure mode to avoid.

### Module layout and the interfaces between them

This is the contract. The modules are written independently against it.

- `src/assets/config.js` — `CONFIG_VERSION`; `parseConfig(text) -> {raw, errors}` (JSON first, then YAML); `normalizeConfig(raw) -> {config, errors, warnings}` (defaults, derived ids, duplicate detection, depth cap of 5, unknown-key warnings); `indexItems(config) -> Map<id, item>`; `resolveTargets(set, config) -> {items, unresolved}`. An issue is `{path: "groups[0].items[2].url", message}`.
- `src/assets/state.js` — `getTheme()`, `setTheme(t)`, `isCollapsed(id, fallback)`, `setCollapsed(id, bool)`, `getQuery()`, `setQuery(s)`. Every `localStorage` access wrapped in try/catch: a private window with storage blocked must still render.
- `src/assets/sets.js` — `openSet(set, config, deps?) -> {opened: number, blocked: Item[], confirmed: boolean}`. `confirmed` is false only when a large set was declined, so the UI can tell a cancel from a zero-target set instead of blaming the popup blocker. Target resolution must be synchronous, since an `await` before the `window.open` calls destroys the user gesture, so `sets.js` imports `resolveTargets` from `config.js` statically; `deps.resolveTargets` exists for tests only and there is exactly one resolver implementation.
- `src/assets/reload.js` — `watchConfig(url, intervalSeconds, onChange, deps?) -> stop()`, where the returned `stop` also carries `stop.refresh({force})` for the manual reload control: `refresh()` polls immediately, `force` additionally omits `If-None-Match` and signals even on unchanged content, because a deliberate reload click should visibly do something. `onChange(text, {etag, hash})`. `deps` may seed `etag` and `body` from the page's initial fetch; unseeded, the first successful `200` counts as a change, which is the safe default because the alternative silently swallows an edit made between the initial fetch and the first poll.
- `src/assets/render.js` — `renderPortal(root, config, handlers)`, `renderIssues(root, errors, warnings)`, `applyFilter(root, query) -> matchCount`. `handlers = {onOpenSet(setId), onToggleGroup(id, collapsed), onOpenItem(item)}`.
- `src/assets/app.js` — wiring only: fetch, parse, render, watch, bind keyboard.

### Served layout is flat, because ConfigMap keys cannot contain slashes

A ConfigMap key must match `[-._a-zA-Z0-9]+`, so a single ConfigMap cannot
reproduce a directory tree. `configMapGenerator` keys files by basename, which
means the repository can keep `src/assets/` and `src/assets/` for the sake of
reading it, while the served tree is flat:

```
/index.html
/app.css  /app.js  /config.js  /render.js  /reload.js  /sets.js  /state.js
/js-yaml.mjs
/config/config.yaml      <- the user's own ConfigMap, mounted nested
```

Consequences that bind the implementation: every import and link is a flat
relative path (`./config.js`, `./js-yaml.mjs`, `./app.css`), basenames across
`src/` must stay unique, and the config URL the app fetches is
`./config/config.yaml`. The user's config is a separate volume mounted at a
path nested inside the app's mount, which Kubernetes supports and which keeps
an app upgrade from touching the user's config or the reverse.

### Validation policy, and the issue paths

Settled while implementing, and binding on the renderer and the docs:

- An issue path is a JSON-ish path (`groups[0].items[2].url`) or the literal
  `config` for a document-level problem such as a parse failure, because the
  renderer prints `path: message` and an empty path renders as `": ..."`.
- **Errors**, which stop the tree rendering: a missing or future `version`, a
  document that is not a mapping, a missing `name` or `url`, broken structure
  such as `items` not being a list, duplicate ids, an unresolvable set target,
  and a `javascript:` or `vbscript:` URL. The CSP does not stop an
  `href="javascript:..."`, and portal configs get copied between people, so that
  one is validation rather than taste.
- **Warnings**, which render anyway: unknown keys, a bad enum value or wrong
  scalar type (falling back to the documented default), and nesting past the
  depth cap.
- Entries that error are dropped from the tree; a partially valid set keeps its
  resolvable targets.
- **What blocks the tree is whether `normalizeConfig` returned a config at all**,
  not the severity or the path of individual issues. It returns none only when
  the document is unusable as a whole: not a mapping, or a missing or future
  `version`. Everything narrower renders the surviving tree with the problems
  listed above it. The renderer must take this from the return value and never
  pattern-match issue paths to decide it.
- `getStoredTheme()` returns `null` when the viewer has never chosen a theme,
  which is what lets a deliberate choice of `auto` still beat `theme` in the
  config. `getTheme()` cannot express that difference and must not be used for
  the precedence decision.
- Ids are global across groups and items, derived ids are the ancestor chain
  joined with `/` (`media/downloads/queue`), and **set ids are a separate
  namespace**, since nothing resolves a set by id.
- `resolveTargets` **de-duplicates by URL**, so a set naming both a group and one
  of its items opens that item once rather than twice. Its `unresolved` entries
  are the raw target strings; turning those into `{path, message}` errors is
  `normalizeConfig`'s job.

### Tests without a toolchain

The test command is `node --test 'tests/**/*.test.mjs'`. A bare directory (`node --test tests/`) no longer works: Node 25 treats the positional as a module entry point and fails with `MODULE_NOT_FOUND`, so CI and the docs must use the glob.

`node:test` and `node:assert` cover `config.js`, `sets.js` and `reload.js` as pure modules, with `fetch` and `window.open` stubbed. No devDependencies, so `node --test tests/` is the whole command and CI needs only a node action. Browser-level behaviour (responsive layout, the palette) is left to a Playwright suite in a later change rather than half-done here.

## Risks / Trade-offs

- **Browsers block multi-tab opens** → detected via `null` from `window.open` and surfaced as a link list, never swallowed.
- **ConfigMap edits never reach a `subPath` mount, and immutable ConfigMaps never change** → documented; our manifests avoid `subPath`.
- **1MiB ConfigMap ceiling** → CI fails if `src/` exceeds 300KiB, long before it matters.
- **Browser-side YAML parsing puts a dependency in the page** → vendored unminified at a pinned version with a recorded hash, and skipped entirely for JSON configs.
- **No status indicators will be the most requested feature** → the reason is written down in the README under a heading people will find, rather than relitigated per issue.
- **Depending on an upstream image we do not control** → pinned, and swapping it is a one-line patch; nothing in the app assumes nginx beyond the cache headers.
- **Derived ids move when a name changes**, losing that group's remembered collapse state → documented; an explicit `id` pins it.

## Migration Plan

New repository, no users, nothing to migrate. Release `v0.1.0` and consume the kustomize base at that tag.

## Open Questions
